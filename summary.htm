Production Caching & Service Worker Architecture Guide

This document presents the complete technical specification for the full-stack caching and Service Worker architecture used by the e-building-flutter-app and society-management-frontend repositories. It explains how web assets are kept up-to-date, how Service Worker background updates operate without user disruption, and how the mobile container interacts with the web application.

1. Architecture Overview (The 2-Layer System)

The application relies on a modern, 2-layer caching strategy that delivers instant updates without interrupting active user workflows:

  1. Layer 1: Server Freshness Rules (Vercel HTTP Revalidation)
    Every time the app opens from a fresh launch, the browser revalidates entry files over the network with Vercel. The server instantly serves the latest index.html if a new deployment was pushed.
  2. Layer 2: Background Auto-Updater (Service Worker & AppRouteWatcher)
    While a session is active, a background Service Worker process checks for new server releases. When a new build is detected, it quietly downloads assets in the background and applies them the moment the user switches screens or resumes the app.

2. Flutter Container Configuration (e-building-flutter-app)

The Flutter mobile app acts as a clean, lightweight native WebView container. Native storage code is streamlined so that Flutter delegates web asset management directly to HTTP and Service Worker protocols.

File / Module Implementation Details Purpose & Rationale
lib/custom_class/utils/local_storage.dart Contains native key-value storage helper methods for FCM tokens, user flags, and redirect links. Maintains clean, minimal native state without tracking unnecessary date timestamps or client-side calculation timers.
lib/ui/screen/web_view/web_view.dart (Mount Logic) Configured _shouldClearCacheOnMount() to return true only when clearCacheOnLoad: true is explicitly passed during active Login or Register flows. Ensures routine entry points (Push Notifications, Deep Links, App Launches) never wipe session cache or log out users, while preserving single-instance protection for post-login redirect chains.
lib/ui/screen/web_view/web_view.dart (Async Clear Block) Uses callAsyncJavaScript with explicit Promise loops for caches.delete() and navigator.serviceWorker.getRegistrations().unregister(). Native Android clearCache() leaves IndexedDB-backed Workbox CacheStorage databases intact. callAsyncJavaScript forces Dart to await complete JS Promise resolution before loading the new page.
notification_services.dart & deep_link_service.dart Explicitly passes clearCacheOnLoad: false across notification taps and deep links. Left UI screens 100% untouched. Guarantees that tapping a push notification or deep link opens the target route directly without clearing user session data.

3. Web Frontend Configuration (society-management-frontend)

The React web application handles application rendering, HTTP header revalidation, and Service Worker background updates:

1. Server HTTP Revalidation Rules (vercel.json)

Implementation: Configured Vercel to attach Cache-Control: no-store, no-cache, must-revalidate, max-age=0 header rules specifically to (index.html|sw.js|registerSW.js).
Rationale: Forces mobile WebViews and desktop web browsers to revalidate entry files over the network on every launch. Cold starts immediately fetch the latest index.html pointing to new build bundles. Hashed asset bundles (images, CSS, JS chunks) retain long-term caching (max-age=31536000, immutable) for sub-second load performance.

2. PWA Auto-Update Setup (package.json & vite-env.d.ts)

Implementation: Added "workbox-window": "^7.3.0" to dependencies and added /// <reference types="vite-plugin-pwa/client" /> in vite-env.d.ts.
Rationale: Resolves Rollup module import references during Vite production builds and provides full TypeScript type declarations for Service Worker registration APIs.

3. Background Route & Visibility Watcher (src/components/AppRouteWatcher.tsx)

Implementation: Built a persistent watcher component using registerSW from virtual:pwa-register. Listens for onNeedRefresh and triggers official updateSW(true) on Client-Side Route Changes (location.pathname) and App Resume (visibilitychange).
Rationale: Service Worker updates download silently in the background. Applying updates on route switches or tab foregrounding prevents disruptive mid-action reloads while ensuring users transition to new builds at the earliest natural opportunity.

4. Root Router Placement (src/app.tsx) & Clean Entry Point (src/main.tsx)

Implementation: Mounted <AppRouteWatcher /> inside <BrowserRouter> in src/app.tsx, keeping src/main.tsx clean and lightweight.
Rationale: Guarantees that AppRouteWatcher stays active continuously across all route switches without extra overhead in the main entry file.

4. How User Actions Are Handled

User Action Handling Layer System Behavior
1. Cold Launch (Opening App) Vercel HTTP Headers Revalidates index.html over network. Loads the latest JS/CSS build assets on launch.
2. Tapping a Push Notification Flutter Route Guard Passes clearCacheOnLoad: false. Target URL loads directly without clearing cache or logging out the user.
3. Tapping a Shared Link (Deep Link) Flutter Route Guard Passes clearCacheOnLoad: false. Opens the target link cleanly while preserving the user's login session.
4. Switching Screens Inside App AppRouteWatcher If a new build was deployed to Vercel while browsing, moving to a new screen automatically reloads the app cleanly onto the new version.
5. Resuming App from Background Visibilitychange Listener If the app was backgrounded while a new build was deployed, bringing the app back to the foreground applies the update immediately.
6. Explicit Login / Registration Flutter Async Clear Block Passes clearCacheOnLoad: true. Executes full callAsyncJavaScript purge (WebStorage, caches.delete(), SW unregistration) to ensure a clean session for the new account.

Preventing Logout on Push Notification Clicks (Flutter Side)

To ensure that tapping a Push Notification opens the requested screen directly without logging out the user or wiping their active session, Flutter handles notification clicks through a 3-step guard flow:

  1. Step 1: Explicit Route Parameter (clearCacheOnLoad: false)
    In lib/services/notification_services.dart, when a push notification is tapped, Flutter navigates to the web view using: 
    Get.offAll(() => WebAppView(url: url, clearCacheOnLoad: false));
    This explicitly instructs the WebView container: "This is a notification tap—do NOT perform a cache wipe."
  2. Step 2: Mount Guard Evaluation (_shouldClearCacheOnMount)
    In lib/ui/screen/web_view/web_view.dart, the mount handler evaluates the parameters: 
    Future<bool> _shouldClearCacheOnMount() async {
  if (_initialCacheDecisionApplied) return false;
  _initialCacheDecisionApplied = true;

  if (widget.clearCacheOnLoad == true) return true;

  final args = Get.arguments;
  if (args is Map && args['clearCacheOnLoad'] == true) return true;

  return false; // Returns false for Notification & Deep Link clicks!
}
    Because clearCacheOnLoad is false, _shouldClearCacheOnMount() returns false.
  3. Step 3: Skipping Cache & Storage Purges
    Because _shouldClearCacheOnMount() returns false, Flutter completely skips calling controller.clearCache() and callAsyncJavaScript(...) (the script that clears localStorage, sessionStorage, IndexedDB caches, and Service Worker registrations).

Result on Notification Tap:

The user's active session, login tokens, and stored preferences remain 100% untouched. The WebView immediately opens the notification target URL (e.g. /notices/123 or /polls/456) with the user remaining logged in seamlessly!
